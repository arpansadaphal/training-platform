### ARCH-032 — Phase 4 UI E2E acceptance criterion rewritten: asserts the unvalidated Assessment state, not "Biggest Opportunity"
Date: 2026-09-26 | Status: FROZEN | Reversible: No — this is a product-behavior commitment, not a tooling choice
Decision: Phase 4's UI E2E (`apps/web/e2e/builder.spec.ts`) asserts the honest unvalidated state instead of the phase file's literal "verify the Assessment screen surfaces it as Biggest Opportunity." Specifically: the test builds a real draft, saves it, asserts that the Assessment panel shows the "Assessment not yet available" heading and its reason paragraph, asserts that none of the validated-only sections (Strengths / Attention areas / Biggest Opportunity / Actions) are present, then commits the draft and asserts the committed version appears on the program detail page.
Rationale: The phase file's original criterion is unsatisfiable against the shipped configuration. `HYPERTROPHY_CONFIG` has every analysis band bound `null` and every axis weight `null` (per Phase 3 and ARCH-029–031), which means `rollUpLeverage` returns BLOCKED for every axis, `computeAssessment` returns `{ kind: "UNVALIDATED" }`, and no axis reaches classification — so there is no "Biggest Opportunity" to surface. Satisfying the literal criterion would require either (a) inventing numeric thresholds, which the freeze forbids (§36, `[SCIENTIFIC INPUT REQUIRED]` items), or (b) introducing a runtime registry-swap seam in the E2E environment, which the kickoff discussion rejected as a production footgun (a misconfigured production environment would silently run on a fixture config — exactly the class of substitution the Phase 9 launch gate exists to prevent). Rewriting the criterion keeps the E2E honest: it asserts what the product actually does today, not what it will do once thresholds are signed off.
Alternatives considered: (1) Test-only fixture config swapped in under `PLAYWRIGHT=1` — rejected as a production footgun and a pre-emption of Phase 9's launch gate. (2) Test against a locally-registered HYPERTROPHY profile with populated thresholds — rejected for the same reason (any runtime seam that lets test configs reach a deployed app is wrong; tests may use fixtures directly via the registry interface, but the deployed app must always use the shipped registry). (3) Skip the E2E until thresholds are signed off — rejected because the point of the test is to enforce the honesty requirement now, not to defer it.
Consequence: Any future phase that ships a validated `HYPERTROPHY_CONFIG` must **extend** this test, not rewrite it. The "Assessment not yet available" expectation will no longer be correct then; the negative assertions (no fabricated bands) become the primary check, and the positive assertions change to the validated shape. The phase file's literal wording — "verify the Assessment screen surfaces it as Biggest Opportunity" — must not be re-attempted in Phase 5+ without first landing the thresholds. Noted in `PROJECT_STATE.md`'s Phase-4-specific outstanding items block.
Source: Phase 4 kickoff exchange Q3; `00-product-freeze-reference.md` invariant 1 and `[SCIENTIFIC INPUT REQUIRED]` list; `06-assessment-engine.md` §"validation gate"; ARCH-029–031.

### ARCH-033 — `CommitOrigin` extended with `draftId` so commit + draft-status-flip are atomic
Date: 2026-09-26 | Status: FROZEN | Reversible: Yes, contained to `packages/api/src/services/programVersionService.ts` and its callers
Decision: `CommitOrigin` is widened from `07-versioning-and-simulation.md`'s literal shape to:
```ts
type CommitOrigin =
  | { via: "MANUAL_COMMIT"; draftId?: string }
  | { via: "AI_APPLIED_SIMULATION"; simulationId: string };
  commitFromMutation accepts this type; when origin.draftId is set, the draft's status is flipped to COMMITTED and its committedAsVersionId is set inside the same transaction that writes the version, revision, snapshot, and active-pointer flip.
Rationale: The doc's literal { via: 'MANUAL_COMMIT' } covers the origin label but not the atomic pairing of "a new version exists" with "the source draft is now committed." Without the pairing, two outcomes are possible and both are wrong: (a) the commit transaction succeeds but the draft stays ACTIVE, so a retry hits the stale check and fails for a reason the user cannot understand; (b) the commit transaction succeeds, the draft-status update runs as a second step and fails, leaving a committed version whose source draft still appears editable. Both are the class of inconsistent-state bug invariant 3 ("no in-place update") and invariant 6 ("detect, don't silently overwrite") exist to prevent. Extending the origin type — rather than adding a second commit function — keeps commitFromMutation as the single function with the single write path, satisfying invariant 2 in both letter and spirit.
Alternatives considered: (1) Two-step commit-then-update-draft — rejected for the recoverable-window reasons above. (2) Add a commitFromDraft variant alongside commitFromMutation — rejected; it would be the second mutation path invariant 2 forbids, even if it delegated internally. (3) Put the draft-status update in a separate service function called after the transaction commits — same recoverable-window failure as (1). (4) Extend the type with a nested object ({ via: 'MANUAL_COMMIT', context: { draftId } }) — rejected as unnecessary ceremony for a single optional field.
Consequence: Phase 8's AI_APPLIED_SIMULATION path will not need a new type; the current shape already fits it. The dormant branch in commitFromMutation that throws on AI_APPLIED_SIMULATION today will be replaced with the equivalent simulation-based stale check (compare simulation.baseVersionId to program.activeVersionId), with no signature change. Any future origin type — e.g., a scheduled/automated commit — extends this union rather than adding a parallel service function. The 07-versioning-and-simulation.md doc's literal CommitOrigin shape is understood to be the abstract form; this entry records the concrete as-built form and the reason for the widening.
Source: Phase 4 kickoff exchange Q1 and Q10; 07-versioning-and-simulation.md §"Composing the invariant" (the commitFromMutation sketch); 00-product-freeze-reference.md invariant 3 and invariant 6.

### ARCH-034 — All three `.env` files must point at the same database; drift produces silent dev-loop breakage
Date: 2026-09-26 | Status: FROZEN | Reversible: Yes, contained to `.env.local`, `apps/web/.env.local`, `packages/db/.env`
Decision: The three local env files — root `.env.local`, `apps/web/.env.local`, `packages/db/.env` — must always point at the same `DATABASE_URL` and `DIRECT_URL`. When switching between local Postgres and the remote `vercel-dev` Neon branch, all three are updated together.
Rationale: `packages/db/.env` is read by Prisma CLI (`migrate`, `db seed`, `db execute`) and by the `packages/db` test suite. `apps/web/.env.local` is read by the Next.js runtime — the dev server, route handlers, RSC, and tRPC procedures — even when those procedures ultimately call through `packages/db`. Root `.env.local` is read by root-level scripts. These readers are independent: Prisma CLI never reads `apps/web/.env.local`, and Next.js never reads `packages/db/.env`. During Phase 4's Builder E2E, `packages/db/.env` had been pointed at local Postgres but the other two files were left pointing at remote Neon. Result: `POST /app/programs` took 8.3 seconds instead of 84 milliseconds, the Program detail RSC hit a Prisma connection-pool timeout (17-connection limit, 10-second acquire), and the Builder route 500'd before the "Open Builder" link rendered — which the E2E reported as a missing locator with no obvious server-side cause. The failure mode is silent: Prisma CLI operations succeed fast, giving the impression that the environment is correct, while Next.js operations crawl and eventually fail in ways that look like application bugs.
Alternatives considered: (1) Startup assertion that all three files point at the same DB — rejected for now. Any check that reads all three files would itself need to know which is authoritative in which context; a runtime assertion in `packages/db` would fire during `migrate deploy` against production (where the files legitimately differ), and a build-time assertion in Next.js would need to run before env files are fully resolved. A Phase-5+ candidate is a small `scripts/check-env-parity.ts` a developer runs manually, or a lint rule that greps the three files for matching `DATABASE_URL` — but neither is a good fit for the current dev workflow. (2) Single `.env` file at root — rejected: Next.js only reads `apps/web/.env.local`; Prisma CLI only reads `packages/db/.env`. The three-file split is imposed by the tooling, not chosen. (3) Symlink `apps/web/.env.local` and `packages/db/.env` to root `.env.local` — rejected: git would track symlinks (fragile across OSes), and each file legitimately needs different vars in some contexts (e.g. `apps/web/.env.local` has `AUTH_SECRET` for Next.js, `packages/db/.env` doesn't).
Consequence: This is a documented convention, not an enforced invariant. A future session that resets local Postgres must update all three files, and the symptom to recognize is: "Prisma CLI is fast, Next.js is slow, RSC hits pool timeout." A Phase-5+ candidate improvement is a pre-test check in `playwright.config.ts`'s `globalSetup` that asserts the three files agree, so an E2E failure never again gets misdiagnosed as a Builder bug. Not built in Phase 4 — the convention plus this entry is the current mitigation.
Source: Phase 4 Builder E2E debugging session; the dev-server log showing an 8.3-second `POST /app/programs` and a 27.7-second RSC 500 with `connection_limit: 17, timeout: 10`.
