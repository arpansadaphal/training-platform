### ARCH-023 — Sentry error delivery on Vercel requires explicit `Sentry.captureException` + `await Sentry.flush()` in route handlers; automatic capture via Next's `onRequestError` is unreliable in Next 15.4+
Date: 2026-09-24 | Status: FROZEN, structural for any route handler expected to reliably deliver to Sentry | Reversible: Conditional — would be revisited if either (a) Next.js fixes the `onRequestError` regression for route handlers, or (b) Vercel changes Lambda freeze behavior
Decision: Any route handler (`app/api/**/route.ts`) that needs reliable Sentry delivery must explicitly call `Sentry.captureException(error)` and `await Sentry.flush(timeoutMs)` before returning. Relying on Next.js's `onRequestError` hook (which `apps/web/instrumentation.ts` exports as `Sentry.captureRequestError`) is insufficient in the current version. The same pattern is documented here for any future async capture path that runs in a Vercel serverless function.

(1) **Vercel Lambda freeze**: the execution environment is frozen immediately after the HTTP response is sent, so Sentry's asynchronous queue never drains — the event is captured but never transmitted. (2) Use `after()` from `next/server` to run capture post-response — valid fallback, but requires the route to return a response immediately (i.e., still removes the throw); the simpler explicit-flush pattern was chosen because it's more obvious in code review. (3) Downgrade Next.js to pre-15.4 — rejected: contradicts ARCH-021's security upgrade.
Consequence: The **Phase 0 Sentry acceptance test's route shape is the reference pattern** — capture explicitly, flush explicitly, return rather than throw. Any future route handler that throws expects its error to reach Vercel logs, but not Sentry, unless it adopts this pattern. `Sentry.captureRequestError` (from `instrumentation.ts`'s `onRequestError` export) is retained in the codebase because it's still correct for RSC render errors and non-route-handler server errors — it's specifically route handlers that need the workaround. Sentry's `debug: true` option requires a debug bundle; setting it in a production build prints "Cannot initialize SDK with `debug` option using a non-debug bundle" and is a no-op, not an error.
Source: Phase 0's Sentry verification exercise — `POST /api/sentry-test` route returned 500 with the error visible in Vercel logs but absent from Sentry Issues, until the explicit-capture + flush pattern was applied.

### ARCH-025 — Turbo env vars declared via `globalEnv` at the config root, not per-task `env` arrays
Date: 2026-09-25 | Status: FROZEN | Reversible: Yes, contained to `turbo.json`
Decision: `turbo.json` declares all build- and runtime-read environment variables in a top-level `globalEnv` array. Per-task `env` arrays are not used. Any new env var the app reads at runtime or build time must be added to `globalEnv`.
Rationale: Phase 1's CI failed with `Environment variable not found: DATABASE_URL` even though the workflow declared `DATABASE_URL` at the job level. Turbo 2.x strips undeclared env vars from task subprocess environments and excludes them from task cache keys — a deliberate design that improves cache correctness but silently breaks tests that need secrets or connection strings. The original `turbo.json` had per-task `env` arrays on `build` only (from ARCH-021), which meant `test` ran without any env vars at all. `globalEnv` applies to every task uniformly, eliminates the per-task duplication, and matches how the docs describe setting env vars that affect more than one task.
Alternatives considered: (1) Add an `env` array to each task that needs it — works, but duplicates the list per-task and requires every future task author to remember to declare env vars; the failure mode is silent (tests fail with "environment variable not found" instead of a config error). (3) Skip the declaration and rely on shell env inheritance — rejected: that's the failure mode Turbo 2.x is designed to prevent.
Consequence: Adding a new env var the app needs is now a two-step process — write it in the platform config (Vercel / CI / local `.env`) and add it to `globalEnv`. A var missing from `globalEnv` will work locally in some contexts and fail in others (specifically: fail under `pnpm turbo run …` in CI, pass under direct `pnpm --filter …` invocation). Documented as a project convention in `PROJECT_STATE.md` so future sessions don't rediscover it.
Source: Phase 1 CI failure log — `pnpm turbo run test` printed `PrismaClientInitializationError: Environment variable not found: DATABASE_URL` while `prisma migrate deploy` (which runs outside Turbo) succeeded with the same job-level env.

### ARCH-026 — Repository `$transaction` calls pass explicit `{ timeout: 20000, maxWait: 10000 }` via a shared `TRANSACTION_OPTIONS` const

Real bugs (a lock cycle, a missing index) will still surface, just after a longer wait. If Phase 3+ introduces longer-running transactions (e.g. commit + AssessmentSnapshot + Revision in one call), the ceiling may need raising again — a one-line change in the shared const. ### ARCH-027 — CI runs against an ephemeral `postgres:16` service container with `prisma migrate deploy` + seed, not against a remote Neon branch

(3) `prisma db:push` instead of `migrate deploy` — rejected for the reason above; a green CI must mean the migration files work, not that the current schema works.

- Local dev (`pnpm dev`) → `vercel-dev` Neon branch
- Local DB tests → `vercel-dev` Neon branch (until local Postgres is adopted — see PROJECT_STATE outstanding items)
- CI → ephemeral `postgres:16` container
- Vercel preview → isolated Neon branch per PR (via Neon integration)

Any change to a migration file must be verified against a *fresh* database at least once (the CI path does this automatically). The service container is Postgres 16; production Neon currently runs Postgres 16-compatible — if that ever diverges, CI's Postgres image must be updated to match. Source: Phase 1 CI failures — `pnpm turbo run test` couldn't reach any database in the workflow's original shape (only placeholder env vars, no service container, no migration step). Fixing this required all three of: service container, job-level env, and Turbo `globalEnv` declaration (ARCH-025).

### ARCH-030 — Assessment-layer result shapes and Fit Score derivation: discriminated unions, an explicit `allAssessedAxes` roll-up, and rule-based ordinal projection (no numeric intermediate)
Date: 2026-09-26 | Status: FROZEN | Reversible: Yes, contained to `packages/domain/src/assessment/types.ts`, `computeAssessment.ts`, `computeFitScore.ts`
Decision: Three coupled structural choices, applied together:
  (1) **Discriminated-union return types.** `computeAssessment` returns `AssessmentResult = { kind: "VALIDATED"; assessment } | { kind: "UNVALIDATED"; reason; assessment }`. `computeFitScore` returns `FitScoreResult = { kind: "VALIDATED"; fitScore } | { kind: "UNVALIDATED"; reason }`. No numeric intermediate, no ordinal→numeric mapping, no averaging. The two categories are config-supplied and provisional.
Rationale: Invariant 8 requires the Fit Score to be "derived from the same leverage roll-up as the qualitative Assessment — never an independently computed number that could disagree with the narrative." Three specific failure modes motivate the design:
  (a) **A bare-string fit score** would let an unvalidated profile produce a "real-looking" band — same class of bug ARCH-028 fixed at the axis level. A discriminated union makes that a type error, not a code-review problem.
  (b) **Reading Fit Score from the surfaced subset** (strengths + attention + biggest opportunity) is unsound against invariant 8: an axis whose severity is below materiality but whose leverage is HIGH would be missed, letting Fit Score and narrative disagree. `allAssessedAxes` is the same collection the narrative was derived from, making "same roll-up" literally true.
  (c) **A weighted sum over categorical leverages** would require an ordinal→numeric mapping (e.g. LOW=1, MEDIUM=2, HIGH=3). That mapping — whatever its values — is a form of threshold invention (Phase-3 guidance item E: "any code that produces a real number from these inputs is a bug"). Ordinal comparison avoids the mapping entirely: `indexOf` yields a rank used only for ordering, never as a magnitude.
Alternatives considered: (1) `Assessment` itself as a discriminated union — rejected: the inner shape is used by consumers that have already narrowed on `AssessmentResult`'s kind, and wrapping at the boundary keeps the doc-compliant inner shape intact. (2) Fit Score taking only the VALIDATED branch — rejected: it would force callers to unwrap the union manually, inviting `as` casts; accepting the union and returning a mirrored one preserves the derivation guarantee across both branches structurally. (3) Numeric weights on `AxisWeight` — folded into ARCH-031. (4) Fit Score derived only from attention/opportunity — rejected as a worse instance of (b). (5) `computeFitScore(result, now)` instead of adding `computedAt` to `Assessment` — rejected: the timestamp is genuinely part of the assessment's identity (it is a pure function of `Analysis.computedAt`), and the doc's signature takes a single parameter. (6) Empty `allAssessedAxes` on a VALIDATED result silently fabricating a band — rejected: throws instead, because that state should be unreachable and a fabricated band would be the exact bug this entry exists to prevent.
Consequence: Every future consumer of `AssessmentResult` or `FitScoreResult` must narrow on `kind` before touching the payload. Adding a new axis does not require a new field on `Assessment` — the axis appears in `allAssessedAxes` automatically. If a later phase needs to re-derive "which axis was worst" or "what was the highest-severity non-opportunity axis," all the inputs are already present. The Fit Score band strings (`STRONG` / `DECENT` / `NEEDS_WORK`) are placeholders pending the (unavailable) Assessment-Redesign source text per Final Freeze Appendix C item 5 — only the string values change if that text is obtained; the derivation guarantee does not. `computeFitScore`'s throw on empty-axes is a defensive guard for an upstream inconsistency in `computeAssessment` — it is not a legitimate runtime path and should never fire in practice.
Source: `00-product-freeze-reference.md` invariant 8; `06-assessment-engine.md` §"Fit Score — guaranteed consistent by construction"; Phase-3 kickoff exchange Q2, Q3, and the Fit Score derivation follow-up.

### ARCH-031 — Config-surface extensions for Phase 3: categorical `AxisWeight.weight`, axis-level fallback keys, and `materialitySeverityThreshold`
Date: 2026-09-26 | Status: FROZEN | Reversible: Yes, contained to `packages/domain/src/analysis/types.ts` + `goal-profiles/hypertrophy.ts` + `rollup.ts`
Decision: Three coupled shape changes to the goal-profile config surface:
  (1) **`AxisWeight.weight` narrowed from `number | null` to `Weight | null`** where `Weight = "LOW" | "MEDIUM" | "HIGH"`. `null` continues to mean "[SCIENTIFIC INPUT REQUIRED]". The leverage table requires the categorical enum (per ARCH-029); a numeric weight would force a numeric→categorical bucketing threshold that does not exist and cannot be invented. Phase 2 never read this field — verified against `volume.ts`, `frequency.ts`, `computeAnalysis.ts`, and `computeRecoveryCostAxis` — so the blast radius is contained to the type declaration and the shipped config.
  (2) **Axis-level fallback keys in `axisWeights`.** The key format is `${axisType}:${scopeKey ?? ''}` per `05-analysis-engine.md`. Phase 3 adds an explicit precedence chain for resolution:
      1. `${axisType}:${scopeKey}` (fully-scoped, e.g. `"VOLUME:chest"`) wins if present.
      2. `${axisType}:` (axis-level fallback, empty scope) is used if the scoped key is absent.
      3. Neither present, OR present with `weight: null` — the axis is UNRESOLVED and the whole roll-up is BLOCKED. Not an error, not a silent default.
      The third step is what makes the design honest: an unresolved key terminates in "we don't know," not a fabricated value. The chain terminates at the *first* key that exists — a scoped key with `weight: null` is an explicit marker, not a fallthrough signal.
  (3) **`materialitySeverityThreshold: Severity` added to `GoalProfileConfig`.** `06-assessment-engine.md` step 6 says the materiality threshold "is also part of the config, not hardcoded in the engine." Type is `Severity` (not `Leverage` and not `Weight`) because step 6 is explicit that the threshold is on severity.
Rationale: (1) is dictated by ARCH-029 — the leverage table's column type is categorical, and any numeric→categorical binning would be threshold invention. (2) is an interpretation of `05-analysis-engine.md`'s key spec: without a fallback, the shipped `HYPERTROPHY_CONFIG.axisWeights` would be an empty object, contradicting the phase file's instruction that it be "structurally complete, but numerically unresolved." The axis-level form lets a config express per-axis defaults without enumerating every muscle-group id, which is seeded data the config does not know. (3) has nowhere else to live — the alternative (a function parameter on `computeAssessment`) would contradict the doc's explicit "config, not engine" statement.
Alternatives considered: (1) Keep `AxisWeight.weight` numeric — rejected: forces a bucketing threshold. (2) Ship `HYPERTROPHY_CONFIG.axisWeights = {}` — rejected: contradicts "structurally complete." (3) Use the scoped key form with a placeholder scope like `"VOLUME:*"` — rejected: introduces a wildcard syntax not in the doc; the empty-scope form was already implied by `${axisType}:${scopeKey ?? ''}`. (4) Fall through a `null` scoped value to the axis-level default — rejected: `null` is an explicit "[SCIENTIFIC INPUT REQUIRED]" marker; falling through would silently substitute an axis-level default for a scope the config author deliberately marked unresolved. (5) `materialitySeverityThreshold` as a function parameter — rejected per the doc's "config" language.
Consequence: A future phase adding a scoped weight (e.g. `"VOLUME:chest": { weight: "HIGH" }`) does not need to touch the axis-level fallback — the scoped key wins by precedence. Removing an axis-level fallback would BLOCK the roll-up for every axis that lacks a scoped override, which is the correct fail-closed behavior for an unconfigured profile. The precedence chain is documented on `GoalProfileConfig.axisWeights` in `analysis/types.ts` and tested in `assessment/__tests__/rollup-precedence.test.ts` (5 cases including the "null does not fall through" case). `materialitySeverityThreshold` is provisional in the shipped config (`"MODERATE"`); changing it changes which attention areas are surfaced but not which axes roll up.
Source: Phase-3 kickoff exchange Decisions #1, #2, #3; `05-analysis-engine.md` key spec; `06-assessment-engine.md` step 6.
