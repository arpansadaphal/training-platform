## Decisions made during implementation

- **"New PR on…", not "New best on…".** The brief's example copy contains "best", which `FORBIDDEN_PATTERNS` bans as an optimality claim (`/\b(optimal|best|ideal)\b/`). Following the brief's own rule that all copy passes the lint, I used the summary's existing wording. If you want "best", the pattern is the thing to change, not the copy.
- **Milestone wording for a new weight is "First session at 60 kg on Back Squat."** The brief's "First time squatting 60 kg" cannot be generated for 110 exercises (no verb per exercise). Generic and factual instead.
- **A "round weight" is a multiple of 5 kg or 5 lb.** The brief said 5 kg. I first used 10 lb for pounds, because a 5 lb step fires a milestone often (a lifter adding 5 lb a session would see one most sessions); the founder changed it to 5 lb before merge, so both units now use a 5 step. A lift's first loaded session never fires (a baseline), and a jump across several round weights names the highest. (Not to be confused with the ARCH-062 progression steps in `loadSteps.ts`, which were already 5 lb for barbell, dumbbell and cable and 10 lb for a machine; they are unchanged.)
- **Weeks since the first session fire at the first logged session at or after 4, 8 and 12 weeks** (the previous one being before the mark), and a long gap names the highest mark crossed. The brief's example said "Six weeks" but its list said 4, 8, 12; I followed the list. **There is nothing after 12 weeks**; a lifter at week 30 gets session-count and weight facts only. Adding 26 and 52 is one line in `WEEK_MILESTONES` if you want it.
- **Priority when several fire: session count > weeks > weight.** One line only, as briefed.
- **"Logged session" = COMPLETED with at least one set.** A session completed with nothing logged is not in the journal and does not count toward "your 10th session". Not asked; it keeps the diary honest and the counts true.
- **A note comes back once.** Only the *immediately previous* COMPLETED session of the same day name is looked at. Alternative: the latest note ever written for that day. Rejected: a lifter who wrote "knee off" in August would be shown it, with an old date, at every session until they wrote another. "Same day name" is case-insensitive and spans programs (the brief said "same day name"); the summary's comparison is per program, so the two definitions differ on purpose.
- **Notes are session-level only, so exercise-level notes were cut** (brief: scope to day-level if that is what exists). Nothing writes `structuredFields.exerciseId`. A future version needs a note box on each exercise card; the Observation model can already hold it.
- **PR rule, units and order match Progress.** Each lift is read in the unit of its newest session. Lifts inside an entry are in the plan's order (`listPrescriptionOrderForUser`), not the order they were logged in: sets logged by "Log remaining sets" share one timestamp, so time order was unstable (I found this when my first API test failed).
- **A lift with no weight (bodyweight) shows its best reps** ("Pull-up × 12") and is never a PR (PRs are by estimated 1RM, which needs a load).
- **CSV:** one row per set; `set_number` is 1-based (stored `setIndex` is 0-based); a `unit` column because a stored load has no unit; the note repeats on each row of its session; the date columns are UTC. Text cells beginning `= + - @` (or tab/CR) get a leading `'` so a spreadsheet does not execute a note as a formula. That changes the exported text of such a note by one character; it is the standard mitigation and I judged it worth it. A UTF-8 BOM is prepended in the route (not in the domain function) so Excel reads non-ASCII notes.
- **Filename date is the server's UTC date.** Off by one for a lifter near midnight in an east or west zone. Cosmetic; passing the local date from the client is the fix if it matters.
- **The note lookup's day is read by session id beside the ownership check** (`findDayOfSessionId`), not after it. My first version read the day after the owned session and made the session page's chain 4 (ceiling 4); this keeps it at 3. The day name read before ownership is proven is only used once ownership has been, and the notes it leads to are filtered by user id regardless.
- **Pagination cursor is the `completedAt` of the oldest entry shown**, compared as an ISO string. Page size 20, max 50. The whole history is loaded each time (see Known issues).
- **No decision record (ARCH-063) was written.** Nothing here changes an invariant, a state machine or a stored shape; the choices above are product judgement recorded in this handoff and PROJECT_STATE. If you want them pinned, ARCH-063 is the next free ID.

## Bugs found and fixed

**Lifts inside a journal entry came out in a different order from run to run** (`journalService.ts`)
- Symptom: my own API test failed ("Arnold Press" listed before "Back Squat"). Not seen by a user; found before shipping.
- Root cause: I ordered a session's lifts by when each was first logged; a batch log stamps every set with the same millisecond, so the order was whatever the sort left.
- Fix: order by the prescription's `orderIndex` in the day, falling back to first-logged time.
- Regression test: `trainingRecord.test.ts` "lists logged sessions newest first…" (asserts the top sets in plan order) and the export ordering test.

**Session page chain went from 3 to 4 with the note lookup** (`sessionService.getSessionPage`)
- Found by `queryBudget.test.ts` (it stayed inside the ceiling of 4, but used all the headroom). Fixed as described under Decisions. The test prints depth 3 again.

No data cleanup is needed for either.

## Known issues / fragile areas

- **Journal and export read the lifter's whole history on every request**, and each "Load older" click rebuilds it (a PR needs the sessions before it). Fine for a year of data (Progress does the same); if a lifter has thousands of sessions, cache the entry list or compute PR flags incrementally.
- **The e2e suite is flaky when run in parallel against `next dev`**: a few specs (different ones each run) time out on `page.goto` while a cold route compiles. In this session `builder-simulate`, `coach`, `landing-dashboard`, `progress-mobile` and `session-ux` each failed once in a parallel run and passed when rerun with `--workers=1`. I believe it is cold-compile contention, not a regression; I did not prove it beyond the serial reruns. CI runs one worker against a production build.
- **"Load older" has no e2e test**, only the API pagination test and a hand check in the browser at 375px with 23 seeded sessions (20, then 3 more, button gone, no horizontal scroll). A permanent e2e would need database access from the Playwright process, which is not set up. The first click on a cold dev server took over 1.5 s to show the new entries.
- **The milestone line is covered by API tests, not e2e** (the 10th session would take ten UI sessions). I looked at it by hand on the seeded user's 10th summary.
- **Duration is `completedAt − startedAt`.** A session started long before its first set, or completed long after its last, shows that long (the existing "since last" timer has the same property). An auto-closed session is completed at its last set's time, so those read correctly.
- **A zero-set completed session** still has a summary page but no journal entry and no milestone.
- **Weight units mix across history only through conversion**: a lift logged in lb then kg is shown in the newest unit and rounded to one decimal ("36.3 kg"). Fine for display; PRs use the same converted numbers.
- **The Today card, Review and the Coach do not link to the journal.** Only the nav does. A "see your journal" link from the Done card is a one-line addition.
- Everything in the previous handoff's Known issues still stands (Vercel region, `todayService`/`resolveRotation` both encoding rotation, never run `next build` under a dev server, the unverified regression test for the rest-day pairing bug, etc.).
