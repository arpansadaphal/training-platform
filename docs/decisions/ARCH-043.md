### ARCH-043 — `AIMessageSegment` is a discriminated union; the model's output schema is a strict subset

Date: 2026-09-27 | Status: FROZEN | Reversible: Yes, contained to `packages/ai/src/types.ts`, `packages/ai/src/schema.ts`, and the mirror at `apps/web/src/types/coach.ts`

Decision: `AIMessageSegment` is a discriminated union on `type` with six variants: `text`, `claim`, `apply_confirmation`, `constraint_notice`, `temporary_constraint_notice`, `grounding_warning`. The `claim` variant requires a non-null `tag` at the type level — a claim segment that lacks a tag cannot be constructed in TypeScript. `apply_confirmation`, `constraint_notice`, and `temporary_constraint_notice` each carry a typed `payload` rather than optional top-level fields. The model's output schema (`modelOutputSchema` in `packages/ai/src/schema.ts`) is a strict subset of the persisted union, restricted to `text` and `claim` only; the four server-produced segment types are excluded from what the model may emit.

Rationale: `10-ai-coach-architecture.md` described `AIMessageSegment` as a single interface with optional fields (`{ type: 'text' | 'claim'; tag?; content; sourceRef? }`). Two problems surfaced during implementation. First, the Phase 8 brief introduced an `apply_confirmation` segment carrying a `{ simulationId, summary }` payload — a shape the single-interface form cannot represent without an ever-growing set of optional fields and without losing type information about which fields are present for which segment types. Second, Final Freeze invariant 7 requires every claim to carry an evidence tag; an optional `tag?` field makes that a runtime check rather than a compile-time one — a claim segment can be constructed without a tag and the type system will not object. Turning invariant 7 into a compile-time property is strictly stronger than a runtime check: a developer writing a new code path that produces a claim segment must supply the tag or the build fails. The strict-subset relationship between `modelOutputSchema` and `aiMessageSegmentSchema` makes it mechanically impossible for the model to emit an `apply_confirmation` segment directly — the schema rejects it, and a rejected final turn never reaches the persistence layer. A model trying to force an Apply button without going through `prepare_apply_confirmation` (and therefore without the ownership check inside that tool) has no path.

Alternatives considered: (a) Keep the single-interface shape with more optional fields. Rejected: loses type information and keeps invariant 7 a runtime-only guarantee. (b) Make `modelOutputSchema` equal to the persisted union and rely on the runtime guard to reject unwanted types. Rejected: makes the model's ability to emit an `apply_confirmation` a runtime check rather than a schema-level impossibility. (c) Move the `AIMessageSegment` mirror into a shared types-only package to avoid duplication with `apps/web/src/types/coach.ts`. Rejected for Phase 8: `16-repository-structure.md` explicitly rules out a types-only package; the duplication is a `Client*`-convention cost, not a design flaw.

Consequence: The client-side `ClientAIMessageSegment` in `apps/web/src/types/coach.ts` mirrors the union by hand, per the repo's `Client*` convention (learning 18). If the server union grows, the client mirror must grow with it; drift surfaces as an unhandled segment type in `SegmentRenderer`, which is exhaustive over the six variants — TypeScript flags the omission at build time. `isWellFormedSegment` in `packages/ai/src/types.ts` is a runtime guard that mirrors the union; a seventh segment type added to the union but not to the guard would slip past the guard and into the persistence layer unrendered, so a future addition must update both.

Source: `10-ai-coach-architecture.md` ("Structured output and evidence tagging"); `phases/phase-08-ai-coach.md`; Phase 8 kickoff exchange Q6 and the `AIMessageSegment` shape refinement.
