### ARCH-075 — A production build migrates and seeds the database before `next build`
Date: 2026-11-17 | Status: Accepted | Reversible: Yes (remove one `&&` link from `apps/web`'s build script) | No application code, schema, migration or UI change.
Supersedes the "not automatically on every deploy" sentence in `docs/15-deployment.md` § Migrations.

Decision: `apps/web`'s build script is `check:provisional-banner && launch-gate && db:deploy && next build`. `db:deploy` (`packages/db/scripts/deploy.ts`) runs `prisma migrate deploy`, then `prisma db seed`, and exits non-zero if either does, which fails the build, so Vercel never promotes the deployment. It runs when `VERCEL_ENV=production`, or when `RUN_DB_DEPLOY=true` (an explicit opt-in for a staging or test-branch environment pointed at a throwaway Neon branch). Everywhere else (Preview, local `pnpm build`, CI) it logs one `[db-deploy] Skipped` line and exits 0. It refuses to start if `DATABASE_URL` or `DIRECT_URL` is missing, or if `DIRECT_URL` is a Neon pooled host. The seed now runs as one transaction under `pg_advisory_xact_lock`.

Rationale: Two production outages (the `isRestDay` migration, October; the cues migration, November) were the same mistake: a schema or seed change merged, deployed, and nobody ran the manual step. The step belongs where the deploy already is. It sits after `launch-gate` so a blocked launch never touches the database, and before `next build` so the schema is ahead of the new code when the new code starts serving.

Alternatives considered: (a) A GitHub Action on merge to `main`. Vercel's Git integration deploys on the same push, in parallel; nothing orders the Action before the deploy unless the Git integration is turned off and the Action drives the deploy, which is a second pipeline, a second copy of the production secrets, and a Vercel Production setup that no longer matches the checklist. Rejected; it stays the fallback if a build ever cannot reach the database. (b) A Vercel pre-build setting in the dashboard. Not in the repo, not reviewed, not testable in CI; the launch gate was put in the build script for the same reason (ARCH-046). Rejected. (c) Run on every environment. A Preview build would apply an unmerged PR's migration to whatever `DATABASE_URL` Preview holds; if that is ever the production database, an abandoned PR changes production. Rejected; production-only by default.

Consequence: Five obligations.
1. **A migration must be safe for the code that is still live.** The database is migrated before the new build, and if `next build` then fails, the old code keeps serving against the new schema. Ship a destructive change (drop or rename a column, add NOT NULL without a default) in two deploys: first stop the code using it, then drop it. The legacy `Exercise.cues` column (ARCH-074) is the next case.
2. **A failed migration blocks every later deploy** with `P3009` until someone resolves it. That is loud, not silent. Fix the SQL or run `prisma migrate resolve` against the production `DIRECT_URL` by hand, then redeploy. See `docs/LAUNCH_CHECKLIST.md` § 3c.
3. **Production needs `DIRECT_URL` (unpooled) and `DATABASE_URL` at build time**, not only at runtime. Both are in `turbo.json`'s `globalEnv`, as is `RUN_DB_DEPLOY` (ARCH-025).
4. **The seed is the source of truth for exercises, involvements and cues** and rewrites them on every production deploy, as it did when run by hand. A row edited directly in production is overwritten.
5. **Neon's free tier has no point-in-time recovery** (`docs/LAUNCH_CHECKLIST.md` § 11). Before merging a destructive migration, take a Neon branch snapshot by hand.
