### ARCH-047 — `coach.openConversation` auto-scopes to the user's primary Program when the caller supplies no scope; `forceNew` bypasses get-or-create
Date: 2026-09-28 | Status: FROZEN | Reversible: Yes, contained to `packages/api/src/routers/coach.ts`, one new export in `packages/api/src/services/identityService.ts`, and one call-site change in `apps/web/app/app/coach/CoachClient.tsx`
Supersedes: the "passing nulls yields a general (unscoped) conversation" clause of ARCH-044. `openConversation` now auto-scopes to the user's primary Program when no scope is supplied. A general (unscoped) conversation is not reachable through the UI in Phase 8.
Decision: When `coach.openConversation` is called with `programId === null` and `programVersionId === null`, the procedure resolves the calling user's primary Program via a new `getPrimaryProgramId(userId)` export on `identityService` and scopes the new conversation to it. The general (unscoped) conversation remains the outcome for users with no non-archived Programs. The procedure accepts an optional `forceNew: boolean`. When `true`, it always creates a new conversation for the resolved scope; when `false` or absent, it uses get-or-create. `/app/coach`'s "+ New" button passes `forceNew: true`. `openConversationForBlock` is unchanged.
Rationale: The `/app/coach` route's "+ New" button was passing `{ programId: null, programVersionId: null }` unconditionally, so every conversation created there was unscoped. `loadScopedProgramVersion` in `routers/coach.ts` short-circuits to `null` at its first check (`if (!conversation.programId) return null;`), so the Coach was handed an empty `currentProgramVersion` and correctly reported that to the user. The user-visible symptom was a Coach that appeared not to know about its own program; the actual defect was a caller that never had a Program id to pass.
Alternatives considered: (a) Fix `CoachClient` to pass the primary Program id resolved server-side — rejected; duplicates "which program is primary" logic and leaves the failure mode available to any future caller. (b) Change the Coach's context builder to fall back to the primary Program when the conversation is unscoped — rejected; collapses two distinct concepts. (c) Require every caller to pass a scope — rejected. (d) Rename "+ New" to reflect get-or-create — rejected as user-hostile.
Consequence: `/app/coach`'s "+ New" button creates a new conversation on every click, each scoped to the user's primary Program. Multiple `(programId, null)` conversations can coexist. The Review path's per-version conversation remains stable and single. Old unscoped conversations created before this decision remain in the sidebar labelled "General"; no data migration is performed.
Source: /app/coach scoping bug observed during Phase 9 GeminiProvider verification; the Phase 9 file's no-new-features constraint; ARCH-044 (superseded clause); ARCH-045.
