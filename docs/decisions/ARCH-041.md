### ARCH-041 — BLOCK_END AssessmentSnapshot writing deferred to Phase 9+
Date: 2026-09-26 | Status: FROZEN | Reversible: Yes, by the explicit Phase 9 trigger below
Decision: Phase 7 does NOT write a `BLOCK_END`-reason AssessmentSnapshot when a TrainingBlock closes. The three Phase 6 lifecycle transaction sites (activateVersion, commitFromMutation, archiveMyProgram) remain unchanged by Phase 7. Review's default view reads the COMMIT-time snapshot only (ARCH-015). The `AssessmentSnapshotReason.BLOCK_END` enum value stays in the schema; the write site is what's deferred.
Rationale: Two independent reasons. (1) **Schema gap.** `AssessmentSnapshot` carries `programVersionId` but no `trainingBlockId`. Under ARCH-016 a single ProgramVersion can open and close multiple TrainingBlocks over its lifetime. A BLOCK_END snapshot tied only to the version would be ambiguous. (2) **No information preserved at MVP.** At MVP `HYPERTROPHY_CONFIG` has every band bound `null` and every axis weight `null`, so every assessment is `UNVALIDATED` (ARCH-032). A BLOCK_END snapshot would be a byte-identical copy of the COMMIT snapshot.
Alternatives considered: (1) Write BLOCK_END snapshots anyway — rejected; `TrainingBlock.endedAt` already marks the moment. (2) Only write BLOCK_END when the recompute would differ — rejected; unreachable at MVP. (3) Add `AssessmentSnapshot.trainingBlockId` in Phase 7 — rejected; violates the phase file's "no migration" scope.
Consequence: **Phase 9** is the trigger to revisit. Phase 9 should: (a) add `AssessmentSnapshot.trainingBlockId String?` with a nullable FK; (b) extend the three lifecycle transaction sites to write a BLOCK_END snapshot inside the same transaction that closes the block (per ARCH-039); (c) update `findLatestAssessmentSnapshotForVersion` to accept an optional `reason` filter. Until then, Review's defensive reason check surfaces schema drift loudly.
Source: Phase 7 kickoff exchange Q4b; Phase 7 phase file; ARCH-015; ARCH-016; ARCH-032; `packages/db/prisma/schema.prisma`.
